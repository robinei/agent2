# Phase 19 — TUI polish

This file is not one bounded feature like the others — it is a running
list of TUI/UX items, each sized and gated on its own. New parts get
appended as they come up; a finished part is not reopened, the way
17_BRANCHES' closed steps aren't. Read `docs/17_BRANCHES.md` Part D
first for the vocabulary this file assumes: `View`, `Focus`,
`ExplicitMode`, the navigator, the dancing gestures (`r`/`v`/`e`/`p`).

## How Part A and B got here

Pressing `e` (armed `ExplicitMode::Rewrite`) and then typing "teste"
submitted `run_program(source: "teste")` verbatim — the gesture is
offered in `View::Chat` and `View::Running` from `Focus::Debug`, with
no visual indicator that the input box has stopped meaning "a chat
message" and started meaning "literal JS source." Two things fell out
of that (the label itself is *not* one — "rewrite" is this project's
own term for this restart, DESIGN.md's "rewrite-with-preserved-
artifacts", and stays exactly that; `run_program` is the mechanism
underneath, not the human-facing name):

- It is a debugging/recovery gesture — replace a suspended or crashed
  program by hand rather than prompting the model to fix it — not
  something that belongs beside ordinary chat. It should only be
  reachable from `View::FullDebug`.
- To be worth anything there, it should hand you the program you are
  replacing, not a blank line: prefilling the input box with the
  current program's source. That is blocked on the input box itself —
  today it can only append to and pop from the *end* (`self.input:
  String`, `push`/`pop`); there is no cursor, no arrow-key movement, no
  multi-line rendering or scrolling. Editing a prefilled program is
  unusable without those.

Part A builds the buffer; Part B relocates the gesture onto it. Part A
stands on its own even before Part B lands — the ordinary chat input
line gets cursor movement and (for anyone who wants it) multi-line
messages for free.

## Part A — A cursor-navigable, multi-line input buffer

### Step A0 — `InputBuffer` (new `debug/input.rs`)

`attach.rs` is already 2200+ lines; this is self-contained editing
logic with no `ratatui`/`Session` dependency, so it gets its own module
and its own unit tests rather than growing `attach.rs` further.

- [ ] A new type, lines stored as `Vec<Vec<char>>` (char-indexed, not
      byte-indexed — a `String`'s byte offsets are not safe cursor
      positions under UTF-8) and a cursor `(row, col)` in that same
      char-indexed space. Name it `InputBuffer`.
- [ ] Construction: `InputBuffer::new()` (one empty line, cursor at
      `(0, 0)`) and `InputBuffer::prefilled(text: &str)` (splits on
      `\n`, cursor at `(0, 0)` — reviewing from the top is the common
      case Part B needs, not resuming at the end).
- [ ] Mutation, each leaving the cursor at the natural resulting
      position:
      - `insert_char(c)` — at the cursor, splitting no line.
      - `insert_newline()` — splits the current line at the cursor into
        two.
      - `backspace()` — deletes the char before the cursor; at column 0
        of a non-first line, joins with the line above (cursor lands at
        the join point, i.e. the old end of the previous line).
      - `delete_forward()` — deletes the char at the cursor; at the end
        of a non-last line, joins with the line below.
      - `kill_to_end()` (Ctrl-K) — deletes from the cursor to the end
        of the **current line only**; does not merge with the line
        below, even at end-of-line (readline's Ctrl-K has no
        multi-line case to translate — this is the sane reading, not
        a corner readline itself defines).
      - `kill_to_start()` (Ctrl-U) — deletes from the start of the
        current line to the cursor. Same one-line scope as `kill_to_end`.
      - `delete_word_backward()` (Ctrl-W) — deletes from the cursor
        back to where `word_left` would land.
      - `delete_word_forward()` (Alt-D) — deletes from the cursor
        forward to where `word_right` would land.
      No kill-ring: none of these save what they deleted anywhere, so
      there is no yank/Ctrl-Y. Common editors offer kill-without-yank
      too; a ring is real functionality, not a gap in this one, and
      goes on the "Later" list at the end of this file if it's ever
      wanted.
- [ ] Movement, all clamped (never past the buffer's start/end, never
      an out-of-range column):
      - `left()` / `right()` — within the line; at a line boundary,
        wraps to the end of the previous / start of the next line.
      - `up()` / `down()` — moves a row, preserving the *target* column
        the cursor is trying to hold (not just the current line's
        length) across a short line and back to a long one — track a
        `sticky_col: usize` set by every horizontal move and by
        `up`/`down` themselves, consulted (not overwritten) by
        `up`/`down`. This is the one piece of state past `lines` +
        `cursor`; name it and its purpose in a doc comment, since
        nothing else in this buffer needs to remember more than the
        current position.
      - `home()` / `end()` — start/end of the current line.
      - `word_left()` / `word_right()` — word-boundary movement, words
        delimited by whitespace (no Unicode word-segmentation — the
        buffer holds program source and chat text, not prose that
        needs it). `word_left` skips any whitespace immediately before
        the cursor, then the word behind that. `word_right` skips the
        remainder of the word under the cursor (if any), then any
        whitespace after it. Both cross line boundaries the same way
        `left`/`right` do.
- [ ] `is_empty(&self) -> bool`, `clear(&mut self)` (back to one empty
      line, cursor `(0, 0)`), `to_string(&self) -> String` (lines
      joined with `\n`).
- [ ] Unit tests, no rendering involved: insertion and deletion at
      start/middle/end of a line; backspace joining lines; delete
      joining lines; up/down through lines of different lengths proving
      `sticky_col` (go right to column 5 on a long line, down to a
      3-char line, down again to another long line — cursor returns to
      column 5); left/right wrapping at line boundaries; word_left/
      word_right over runs of whitespace and across a line boundary;
      kill_to_end/kill_to_start staying within one line even when
      called at that line's start/end; delete_word_backward/forward at
      a word boundary and mid-word; `prefilled` round-trips through
      `to_string`.
- [ ] Gate.

### Step A1 — Wire it into `on_input_key` (`attach.rs`)

- [ ] `AttachedApp.input: String` becomes `input: InputBuffer`.
      Callers that read `app.input` as a string (rendering, the
      timeline, tests) use `.to_string()`; callers that check emptiness
      use `.is_empty()`.
- [ ] `on_input_key`: `KeyCode::Char(c)` (no modifiers, or only Shift —
      see the Ctrl/Alt table below) calls `insert_char`;
      `KeyCode::Backspace` calls `backspace`; `KeyCode::Delete` calls
      `delete_forward` (new — free once the buffer has forward delete,
      and there is no reason to leave it out); `KeyCode::Left/Right/Up/
      Down/Home/End` call the matching movement. `KeyCode::Enter`'s
      existing behavior (submit) is unchanged — it does **not** insert
      a newline.
- [ ] The common readline/emacs subset, as Ctrl/Alt+letter — reliable
      everywhere modifier+Enter wasn't: Ctrl+`letter` is a distinct,
      unambiguous control byte in every terminal's legacy encoding, and
      Alt+`letter` (unlike Alt+Enter) has no non-modified meaning of
      its own for a terminal or window manager to have already claimed
      (see the superseded note on 18_TARGETING Step A1, and what
      motivated `arm_ask`). One `match` arm per row:

      | Key | Calls | Also bound to |
      |---|---|---|
      | Ctrl-A | `home()` | `Home` |
      | Ctrl-E | `end()` | `End` |
      | Ctrl-B | `left()` | `Left` |
      | Ctrl-F | `right()` | `Right` |
      | Ctrl-P | `up()` | `Up` |
      | Ctrl-N | `down()` | `Down` |
      | Ctrl-D | `delete_forward()` | `Delete` |
      | Ctrl-H | `backspace()` | `Backspace` |
      | Ctrl-K | `kill_to_end()` | — |
      | Ctrl-U | `kill_to_start()` | — |
      | Ctrl-W | `delete_word_backward()` | — |
      | Alt-B | `word_left()` | — |
      | Alt-F | `word_right()` | — |
      | Alt-D | `delete_word_forward()` | — |
      | Ctrl-O | `insert_newline()` | — |

      Ctrl-H is included because some terminals send it in place of
      `KeyCode::Backspace` for the physical Backspace key — an alias,
      not a new gesture. Ctrl-D deliberately does **not** carry
      readline's "EOF on an empty line" meaning; there is no exit
      gesture on this key here, only forward-delete, so it can't be
      hit by accident while editing.
- [ ] Gate.

### Step A2 — Render multi-line, with scrolling (`attach.rs`)

- [ ] The input area's `Layout` constraint grows from a fixed small
      height to `Constraint::Length(n.clamp(3, max))`, where `n` is the
      buffer's line count + 2 (borders) and `max` is a fraction of the
      terminal height (pick one — a quarter is reasonable, named as a
      constant) so a long prefilled program does not push the chat pane
      out of existence.
- [ ] Within that area, scroll to keep the cursor's row visible —
      same top/end slicing shape `render_chat` already uses for the
      transcript (`lines[top..end]`), not a new pattern. No horizontal
      scrolling: a line wider than the box wraps (`textwrap`, already a
      dependency) rather than running off the edge.
- [ ] The cursor glyph (`▏`) moves to the actual cursor position — row
      and column within the visible slice — rather than always
      trailing the last line.
- [ ] Gate.

## Part B — "rewrite" becomes a debugger-only gesture

The name stays `ExplicitMode::Rewrite` / "rewrite" throughout this
part — see the intro above. Only where it's reachable from, and what
it starts you with, change.

### Step B0 — Relocate (`attach.rs`)

- [ ] The `e`-key binding in `on_debug_key`
      (`if self.view != View::FullDebug`) is deleted — the gesture no
      longer lives in `Chat`/`Running`.
- [ ] A new binding, active **only** in `View::FullDebug` (today's
      FullDebug key set — `d`/esc/tab/1-9/space/s/n/q — does not use
      `r`, so it's free): `KeyCode::Char('r')` returns a new
      `KeyAction::ArmRewrite`. Pure `on_key`/`on_debug_key` stays
      `Session`-free, so arming (which needs the current program's
      source — see B1) is a `KeyAction` the driving loop resolves, the
      same division already used for `Fork`/`Interrupt`/etc.
- [ ] The footer hints (`FullDebug`'s two variants) gain `r rewrite`;
      the `Chat`/`Running` `Focus::Debug` hints lose it.
- [ ] Gate.

### Step B1 — Prefill from the current program (`attach.rs`)

- [ ] In `run_attached`'s main loop, `KeyAction::ArmRewrite` calls
      `resolve_program(app, &session)`, takes `pv.source` (the
      `ProgramView` half — present for the current program whether or
      not it also has a live VM), and:
      - if there is no selected program at all (`pv` is `None` —
        nothing has ever run on this branch), arms with an **empty**
        buffer, same as today's blank-line start;
      - otherwise arms with `InputBuffer::prefilled(&pv.source)`.
      Either way: `app.explicit_mode = Some(ExplicitMode::Rewrite)`,
      `app.focus = Focus::Input`.
- [ ] The input box's title (the same `match` that now shows `" ask "`
      for `ask_armed`) grows a case for
      `explicit_mode == Some(ExplicitMode::Rewrite)`: `" rewrite "`.
      The other three explicit modes get the same treatment in Part C,
      not here — this step only needs its own.
- [ ] New test: arming from `View::FullDebug` with a resolved program
      source populates the buffer with that source, cursor at `(0, 0)`;
      arming with nothing to resolve leaves it empty. (This test needs
      a `Session`/`ProgramView` fixture — follow the pattern an
      existing `FullDebug` rendering test already builds one from,
      rather than inventing a second.)
- [ ] Gate.

## Part C — Every modal thing gets feedback, in and out

Found stepping back for a whole-UI read: every surprise hit in this
file so far (Alt+Enter, the `e`/rewrite bug, the meaningless `w` hint)
is a variant of one thing — a mode changes with nothing shown for it.
Four steps, all the same pattern: every modal thing gets feedback, and
a clear, consistent way both in and out of it.

### Step C0 — Title indicator for the remaining three modes (`attach.rs`)

- [ ] The input-box title `match` (extended for `ask_armed` and
      `Rewrite` above) grows the last three cases:
      `ExplicitMode::Rename` → `" rename "`, `ResumeWithValue` →
      `" resume "`, `SpawnCharter` → `" spawn "`. Same style, same
      color (`Color::Yellow`) as the existing armed cases — armed is
      armed, regardless of which mode.
- [ ] Gate.

### Step C1 — A shared `disarm`, used by a branch switch (`attach.rs`)

- [ ] A new `AttachedApp::disarm(&mut self)`: clears `explicit_mode`,
      `ask_armed`, and `last_clicked_event` (the fork-from-here target
      C2 below makes visible) together — one place that means "back to
      the neutral state," since it's about to grow a second caller.
      **`self.input` and `self.focus` are never touched by it** — a
      typed draft surviving a context change is normal chat-app
      behavior; an armed `rename`/`rewrite`/etc. call, or a stale fork
      target, silently firing against something you didn't mean is the
      actual danger, the same shape as the `e` bug.
- [ ] `select_branch` calls `self.disarm()` instead of its own
      standalone `self.last_clicked_event = None` line — same effect,
      now also covering the two fields it was missing.
- [ ] New test: arm `Rewrite` (or any mode) and set a fork target,
      select a different branch, assert all three are cleared; type
      first, arm second, select a different branch, assert the typed
      text is still there.
- [ ] Gate.

### Step C2 — A clicked message is a real, visible, toggleable selection (`attach.rs`)

Clicking a chat row already sets `last_clicked_event`, but nothing
shows *which* row that is, and today it's only consumed by a
capital-`F` you have to know to reach for — proven confusing in
practice: click a message, press `f` from habit, and it silently
forks from the branch's leaf instead, because `f` and `F` are two
unrelated bindings and only one of them reads the click. Fix the
cause, not the symptom: once the selection is visible, one key acting
on it is the obvious design, not a second modifier-cased key to
remember.

- [ ] Clicking a chat row **toggles** `last_clicked_event`: clicking
      the already-selected row's id clears it back to `None`
      (deselect), clicking a different one sets it. (Still gated the
      same way as today — the streaming sentinel id is never
      selectable.)
- [ ] `render_chat`'s per-row style: alongside the existing
      `selected_subitem` highlight (`app.selected_subitem`, reversed
      style), add the same treatment when `Some(*id) ==
      app.last_clicked_event` — a selected message is highlighted the
      same way a selected subitem already is, not a new visual
      language.
- [ ] `F` is deleted; `f` alone carries both meanings `on_debug_key`
      already has for `F`: `Some(id) => KeyAction::ForkAt(id)`,
      `None => KeyAction::Fork`. A message selected → fork from it; none
      selected → fork from the leaf, today's plain `f`. `ForkAt` (the
      `KeyAction` variant) and its handling in the main loop are
      unchanged — only which key reaches them changes.
- [ ] The footer hints' `f/F fork` becomes `f fork`.
- [ ] New tests: clicking a row sets `last_clicked_event`; clicking the
      same row again clears it; clicking a different row replaces it.
      `fork_interrupt_and_jump_keys` (attach.rs) loses its `F`
      assertions and gains their replacements on plain `f`: with no
      selection, `Fork`; with `last_clicked_event` set, `ForkAt`.
- [ ] Gate.

### Step C3 — Clicking the input box focuses it and disarms (`attach.rs`)

Clicking inside the message box today does nothing — it isn't a
`Pane`, so `pane_at` never matches it and `on_click` falls through.
Worse: the *chat* pane's registered rect (`render_chat`'s returned
`area`) currently spans the whole chat column including the input
box's rows, so a click that lands there is silently misread as an
out-of-range chat-transcript row index rather than going anywhere
sensible.

- [ ] `Pane` gains an `Input` variant. Its mouse-wheel arm is a no-op
      (`Pane::Input => {}`, same as `Pane::Navigator`'s already is) —
      only click behavior is new here.
- [ ] `render_chat` registers the input box's own rect for `Pane::Input`
      (`app.pane_rects.push((Pane::Input, ...))`, the same way the
      chat/navigator/source panes already register theirs) instead of
      only returning the outer chat `area`, so a click there is routed
      correctly rather than folded into `Pane::Chat`'s row math.
- [ ] `on_click`'s new `Pane::Input` arm: `self.focus = Focus::Input;
      self.disarm();`. Typed text is untouched, same reasoning as C1 —
      clicking in to keep typing shouldn't cost you a draft, only
      whatever mode or selection was active before.
- [ ] New test: with an explicit mode armed and a fork target set,
      clicking the input box's rect focuses it and clears both, typed
      text unchanged.
- [ ] Gate.

## Part D — Timeline scrolling (`attach.rs`)

`render_timeline` renders every row into one `Paragraph` with no
top/end slice at all — unlike `render_chat`, which already has this
exact shape. On a timeline longer than the screen, `j`/`k` walk
`timeline_cursor` off the visible rows with no feedback that it moved.

### Step D0

- [ ] `render_timeline` computes a `top` the same way `render_chat`
      does: clamp so `timeline_cursor` always falls within
      `top..top+visible`. No new scroll field — the timeline has no
      independent manual-scroll input (only `j`/`k`, which move the
      cursor), so the viewport is a pure function of the cursor and the
      area height, recomputed every frame.
- [ ] New test: a timeline longer than a small fixed visible height,
      cursor moved past the bottom, asserts the rendered slice's start
      index has advanced enough to keep the cursor's row inside it.
- [ ] Gate.

## Part E — Cap the navigator's height and let it scroll

`Pane::Navigator`'s height is `Constraint::Length(branches().len() +
2)` — uncapped, so a deep fork/spawn tree grows it to consume the
whole screen, squeezing chat/source/console down or off. Navigator
mouse-wheel scroll is a deliberate no-op today (`Pane::Navigator =>
{}`), which is only safe because nothing caps the height forcing a
scroll in the first place — capping without adding scroll would just
hide branches with no way back to them.

### Step E0

- [ ] Cap the navigator's `Constraint::Length` at
      `(branches().len() + 2).min(cap)`, `cap` a named constant (a
      third of the terminal height is reasonable — pick one, name it,
      matching how 19_UX Part A names its own input-box height cap).
- [ ] Add `navigator_scroll: Option<usize>` to `AttachedApp` (same
      `Option<usize>` shape as `chat_scroll`/`console_scroll`/etc.):
      `None` means auto-follow the selected branch's row (top/end
      slicing again, same pattern a third time), `Some(n)` means a
      manual scroll is in effect.
- [ ] The navigator's `Pane::Navigator` arm in the mouse-wheel handler
      stops being a no-op: it now sets `navigator_scroll` the same way
      the other scrollable panes' wheel handling already does.
- [ ] Selecting a different branch (`select_branch`) resets
      `navigator_scroll` to `None` — auto-follow wins back once you've
      navigated, the same reasoning `chat_scroll`'s own auto-reset
      already uses (`auto_reset_chat_scroll`).
- [ ] New test: more branches than a small fixed cap, selecting one
      near the end scrolls it into view; a manual wheel-scroll is
      overridden back to auto-follow on the next `select_branch`.
- [ ] Gate.

## Part F — A shortcut is visible only when it would do something

`w waiting` already only shows when a branch is actually waiting on
you. `v resume` doesn't get the same treatment, and unlike `w` it has
a real cost: `Runner::eligible`'s `Restart::Resume` arm (`machine.rs`)
is `Ok` only for `Phase::Suspended` on a resumable condition, refused
everywhere else with "nothing is suspended." Arm it, type a value, hit
Enter on a branch that isn't suspended, and it goes through the exact
same machinery an LLM turn does (`cmd_restart` → `state.take_turn`)
just to come back refused — a wasted action, not a harmless no-op like
`w` on an empty wait-list.

Checked the other three: `Restart::RunProgram` is explicitly "always
valid" in `eligible`, and `cmd_rename`/`cmd_spawn` (`host/mod.rs`) have
no phase check at all — `resume` is the one outlier, not a sign of a
broader audit needed.

### Step F0 — The selected branch's status reaches key handling (`attach.rs`)

- [ ] `on_key`/`on_debug_key` gain a `selected_status: Option<&str>`
      parameter — the selected branch's `BranchInfo.status`, borrowed
      from the `infos` the driving loop already computes each tick, not
      a new query. Stays pure/`Session`-free like the rest of `on_key`,
      same reasoning `KeyAction::ArmRewrite` (Part B0) already used for
      needing session data.
- [ ] Existing callers (the main loop, every test constructing a key
      event) pass it through; tests exercising a suspended vs.
      non-suspended selected branch pass `Some("suspended")` /
      `Some("idle")` / `None` (no branch selected) as fits the case
      under test.
- [ ] Gate.

### Step F1 — Gate `v` on it, in both the key and the hint (`attach.rs`)

- [ ] `on_debug_key`'s `'v'` arm only calls
      `self.arm(ExplicitMode::ResumeWithValue)` when
      `selected_status == Some("suspended")`; otherwise falls through
      to `KeyAction::None`, same as an unmapped key — pressing it when
      it wouldn't do anything is silently inert, not an error.
- [ ] The footer's `waiting` local (already computed for `w`) gets a
      sibling `resumable = selected_status == Some("suspended")`, and
      `v resume` is appended to the hint only when `resumable` — same
      `if cond { " · v resume" } else { "" }` shape `w waiting` already
      uses.
- [ ] New tests: `on_debug_key('v', ..., Some("suspended"))` arms the
      mode; `on_debug_key('v', ..., Some("idle"))` and `(..., None)`
      are both `KeyAction::None`; the footer hint contains `v resume`
      only when `resumable` is true.
- [ ] Gate.

## Later, not yet scheduled

Real, but lower priority than A–E — pick these up as their own part
when it's their turn:

- **A help/cheatsheet screen.** The whole key model today is pieced
  together from a dense, tiny, single-line footer hint that changes
  shape per `(View, Focus)`. Worth a dedicated overlay (`?` is free
  everywhere) rather than trying to make the footer line say more.
- **Clickable "agent N" mentions look like plain text.** `on_click`'s
  `RowDetail::None` branch makes them jump branches, but nothing in
  the rendering marks a mention as clickable versus ordinary prose.
- **The navigator's own title omits Tab.** It lists `w jump · t
  timeline` but not Tab, the more basic cycle-branch gesture that's
  intercepted globally before any other key logic runs. Small — fold
  into whichever future step next touches that title line.
- **A kill-ring, with Ctrl-Y to yank.** Part A's Ctrl-K/Ctrl-U/Ctrl-W/
  Alt-D delete without saving anything. A ring that remembers the last
  kill and a paste-back gesture is real, separable functionality, not
  a piece Part A is missing.
