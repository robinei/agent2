# Phase 19 — TUI polish

This file is not one bounded feature like the others — it is a running
list of TUI/UX items, each sized and gated on its own. New parts get
appended as they come up; a finished part is not reopened, the way
17_BRANCHES' closed steps aren't. Read `docs/17_BRANCHES.md` Part D
first for the vocabulary this file assumes: `View`, `Focus`,
`ExplicitMode`, the navigator, the dancing gestures (`r`/`v`/`e`/`p`).

## How Part A and B got here

Pressing `e` (armed `ExplicitMode::Rewrite`) and then typing "teste"
submitted `run_program(source: "teste")` verbatim — the gesture is
offered in `View::Chat` and `View::Running` from `Focus::Debug`, with
no visual indicator that the input box has stopped meaning "a chat
message" and started meaning "literal JS source." Three things fell out
of that:

- The user-facing label is wrong. It is internally and in the footer
  called "rewrite," but the restart it issues is `run_program` — the
  same one offered to the LLM, and the same word should describe it to
  a human.
- It is a debugging/recovery gesture — replace a suspended or crashed
  program by hand rather than prompting the model to fix it — not
  something that belongs beside ordinary chat. It should only be
  reachable from `View::FullDebug`.
- To be worth anything there, it should hand you the program you are
  replacing, not a blank line: prefilling the input box with the
  current program's source. That is blocked on the input box itself —
  today it can only append to and pop from the *end* (`self.input:
  String`, `push`/`pop`); there is no cursor, no arrow-key movement, no
  multi-line rendering or scrolling. Editing a prefilled program is
  unusable without those.

Part A builds the buffer; Part B moves and renames the gesture onto it.
Part A stands on its own even before Part B lands — the ordinary chat
input line gets cursor movement and (for anyone who wants it) multi-line
messages for free.

## Part A — A cursor-navigable, multi-line input buffer

### Step A0 — `InputBuffer` (new `debug/input.rs`)

`attach.rs` is already 2200+ lines; this is self-contained editing
logic with no `ratatui`/`Session` dependency, so it gets its own module
and its own unit tests rather than growing `attach.rs` further.

- [ ] A new type, lines stored as `Vec<Vec<char>>` (char-indexed, not
      byte-indexed — a `String`'s byte offsets are not safe cursor
      positions under UTF-8) and a cursor `(row, col)` in that same
      char-indexed space. Name it `InputBuffer`.
- [ ] Construction: `InputBuffer::new()` (one empty line, cursor at
      `(0, 0)`) and `InputBuffer::prefilled(text: &str)` (splits on
      `\n`, cursor at `(0, 0)` — reviewing from the top is the common
      case Part B needs, not resuming at the end).
- [ ] Mutation, each leaving the cursor at the natural resulting
      position:
      - `insert_char(c)` — at the cursor, splitting no line.
      - `insert_newline()` — splits the current line at the cursor into
        two.
      - `backspace()` — deletes the char before the cursor; at column 0
        of a non-first line, joins with the line above (cursor lands at
        the join point, i.e. the old end of the previous line).
      - `delete_forward()` — deletes the char at the cursor; at the end
        of a non-last line, joins with the line below.
- [ ] Movement, all clamped (never past the buffer's start/end, never
      an out-of-range column):
      - `left()` / `right()` — within the line; at a line boundary,
        wraps to the end of the previous / start of the next line.
      - `up()` / `down()` — moves a row, preserving the *target* column
        the cursor is trying to hold (not just the current line's
        length) across a short line and back to a long one — track a
        `sticky_col: usize` set by every horizontal move and by
        `up`/`down` themselves, consulted (not overwritten) by
        `up`/`down`. This is the one piece of state past `lines` +
        `cursor`; name it and its purpose in a doc comment, since
        nothing else in this buffer needs to remember more than the
        current position.
      - `home()` / `end()` — start/end of the current line.
- [ ] `is_empty(&self) -> bool`, `clear(&mut self)` (back to one empty
      line, cursor `(0, 0)`), `to_string(&self) -> String` (lines
      joined with `\n`).
- [ ] Unit tests, no rendering involved: insertion and deletion at
      start/middle/end of a line; backspace joining lines; delete
      joining lines; up/down through lines of different lengths proving
      `sticky_col` (go right to column 5 on a long line, down to a
      3-char line, down again to another long line — cursor returns to
      column 5); left/right wrapping at line boundaries; `prefilled`
      round-trips through `to_string`.
- [ ] Gate.

### Step A1 — Wire it into `on_input_key` (`attach.rs`)

- [ ] `AttachedApp.input: String` becomes `input: InputBuffer`.
      Callers that read `app.input` as a string (rendering, the
      timeline, tests) use `.to_string()`; callers that check emptiness
      use `.is_empty()`.
- [ ] `on_input_key`: `KeyCode::Char(c)` calls `insert_char`;
      `KeyCode::Backspace` calls `backspace`; `KeyCode::Delete` calls
      `delete_forward` (new — free once the buffer has forward delete,
      and there is no reason to leave it out); `KeyCode::Left/Right/Up/
      Down/Home/End` call the matching movement. `KeyCode::Enter`'s
      existing behavior (submit) is unchanged — it does **not** insert
      a newline.
- [ ] `KeyCode::Char('o') if key.modifiers.contains(KeyModifiers::CONTROL)`
      calls `insert_newline` — Ctrl+O ("open a line"), not a modifier on
      Enter: Ctrl+`letter` is a distinct, unambiguous control byte in
      every terminal's legacy encoding (unlike modifier+Enter — see the
      superseded note on 18_TARGETING Step A1), so this is exactly the
      kind of gesture that survives the KDE/Konsole-class conflict that
      motivated `arm_ask`.
- [ ] Gate.

### Step A2 — Render multi-line, with scrolling (`attach.rs`)

- [ ] The input area's `Layout` constraint grows from a fixed small
      height to `Constraint::Length(n.clamp(3, max))`, where `n` is the
      buffer's line count + 2 (borders) and `max` is a fraction of the
      terminal height (pick one — a quarter is reasonable, named as a
      constant) so a long prefilled program does not push the chat pane
      out of existence.
- [ ] Within that area, scroll to keep the cursor's row visible —
      same top/end slicing shape `render_chat` already uses for the
      transcript (`lines[top..end]`), not a new pattern. No horizontal
      scrolling: a line wider than the box wraps (`textwrap`, already a
      dependency) rather than running off the edge.
- [ ] The cursor glyph (`▏`) moves to the actual cursor position — row
      and column within the visible slice — rather than always
      trailing the last line.
- [ ] Gate.

## Part B — "run program" becomes a debugger-only gesture

### Step B0 — Rename and relocate (`attach.rs`)

- [ ] `ExplicitMode::Rewrite` is renamed `ExplicitMode::RunProgram`
      (the type name should say what it does, same reasoning as the
      user-facing label). Its one match arm in `resolve_submit_mode`
      is unchanged in behavior.
- [ ] The `e`-key binding in `on_debug_key`
      (`if self.view != View::FullDebug`) is deleted — the gesture no
      longer lives in `Chat`/`Running`.
- [ ] A new binding, active **only** in `View::FullDebug` (today's
      FullDebug key set — `d`/esc/tab/1-9/space/s/n/q — does not use
      `r`, so it's free): `KeyCode::Char('r')` returns a new
      `KeyAction::ArmRunProgram`. Pure `on_key`/`on_debug_key` stays
      `Session`-free, so arming (which needs the current program's
      source — see B1) is a `KeyAction` the driving loop resolves, the
      same division already used for `Fork`/`Interrupt`/etc.
- [ ] The footer hints (`FullDebug`'s two variants) gain `r run
      program`; the `Chat`/`Running` `Focus::Debug` hints lose the old
      `e rewrite` / (already-absent) mention.
- [ ] Gate.

### Step B1 — Prefill from the current program (`attach.rs`)

- [ ] In `run_attached`'s main loop, `KeyAction::ArmRunProgram` calls
      `resolve_program(app, &session)`, takes `pv.source` (the
      `ProgramView` half — present for the current program whether or
      not it also has a live VM), and:
      - if there is no selected program at all (`pv` is `None` —
        nothing has ever run on this branch), arms with an **empty**
        buffer, same as today's blank-line start;
      - otherwise arms with `InputBuffer::prefilled(&pv.source)`.
      Either way: `app.explicit_mode = Some(ExplicitMode::RunProgram)`,
      `app.focus = Focus::Input`.
- [ ] The input box's title (the same `match` that now shows `" ask "`
      for `ask_armed`) grows a case for
      `explicit_mode == Some(ExplicitMode::RunProgram)`: `" run program
      "`. *(The other three explicit modes — rename/resume/spawn — stay
      untitled, as today; giving every explicit mode its own title is a
      fine follow-up but is not this step.)*
- [ ] New test: arming from `View::FullDebug` with a resolved program
      source populates the buffer with that source, cursor at `(0, 0)`;
      arming with nothing to resolve leaves it empty. (This test needs
      a `Session`/`ProgramView` fixture — follow the pattern an
      existing `FullDebug` rendering test already builds one from,
      rather than inventing a second.)
- [ ] Gate.
